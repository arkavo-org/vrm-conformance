# CCD (continuous-collision / tunneling) conformance coverage

**Date:** 2026-05-30
**Status:** Design — awaiting review
**Motivation:** VMK follow-ups *sleeve→arm* and *skirt→leg* are continuous-collision-detection (CCD) failures — a spring-bone/cloth chain tunnels through a collider under fast relative motion. The suite has no signal for this: collider sweeps are static or gently-swung (0.6 m/s ≈ 1 cm/substep at 60 Hz against 3–5 cm colliders — firmly in the discrete-collision-works regime), and pass/fail is SSIM/consensus, which cannot reliably catch a transient tunnel. This adds a fast-motion regime and a renderer-independent penetration metric so a renderer that tunnels fails a test.

## Decisions (locked during brainstorming)

1. **Endpoint:** production CCD conformance coverage (infra + parametric sweep + cross-renderer run + findings), not a spike.
2. **Metric:** absolute, renderer-independent **non-penetration invariant** — across all captured frames, no chain joint may sit inside the (suite-authored, hence known) collider surface beyond a tolerance: `min signed_distance(joint, collider) ≥ −ε`. No oracle; the collider geometry is generated by the suite.
3. **Motion:** reuse `animate_root_transform` at a new **fast regime** + a **world-fixed collider** (`ColliderAttach::WorldCoordinates`, already exists). The avatar translates fast so the chain sweeps through the stationary collider. No new motion op.

## What exists (verified) vs what's new

Exists and reused:
- `dump_bone_positions` op → `DumpBonePositionsResult { springs: [{ spring_index, joint_positions: Vec<[f32;3]> }] }` (world-space, metres) — `crates/vrm-ops/src/tools.rs`.
- `vrm_diff_engine::positions::diff_positions` (per-joint + chain drift vs a reference) — the engine pattern to mirror.
- `render_sequence` op + per-frame PNG capture (RFC-0004), implemented by all four adapters; the adapter runs the per-frame physics loop internally and returns all frames in one call (`crates/vrm-runner/src/execute.rs` dispatches `adapter.call("render_sequence", …)` once).
- `ColliderAttach::WorldCoordinates` (`crates/vrm-asset-generator/src/params.rs`).
- `execute_plan_capturing_positions` (`execute.rs`) — captures a **single** `dump_bone_positions` at the end of the plan.

New (the actual cost):
- **Per-frame** joint positions during a sequence (today only a single end-of-plan instant exists; a transient tunnel that recovers would be missed end-only).
- A penetration metric (signed distance to a known collider, min over frames).
- A fast-motion CCD asset sweep + sidecar.
- A cross-renderer run + findings.

## Architecture (four phases, one coherent capability)

### Phase 1 — Per-frame position capture via a `render_sequence` result extension

The adapter already steps physics per frame inside `render_sequence` and already returns per-frame PNG metadata. Add an **optional per-frame joint-positions payload** to that same result:

- `RenderSequenceResult.frames[i]` gains optional `spring_positions: Vec<SpringPositions>` (reusing the existing `SpringPositions` type — `{ spring_index, joint_positions: Vec<[f32;3]> }`).
- Gated by a request flag in the `render_sequence` params (e.g. `capture_positions: bool`, default false) so existing sequence tests are unaffected and the payload is only produced when asked.
- Each adapter reports, at each captured frame, the world-space joint positions it already holds — no new stepping model, no new op. BLAKE3/sentinel handling for the positions payload mirrors the existing per-frame PNG centralisation in the runner (`execute.rs::rehash_frames` / batch loop) — positions are small JSON, so they may be inlined rather than ref'd; the runner persists them to a per-test `<id>_<renderer>_positions.json`.
- **UniVRM (batched one-shot):** per-frame position emission from the batch path is the hardest integration. Since the metric is absolute per-renderer, UniVRM is **best-effort** — if its batch path can emit per-frame positions, include it; otherwise the per-op adapters (VMK — the target — godot, three-vrm) carry the signal and UniVRM is recorded as "no per-frame capture" rather than blocking.

**Boundary:** this is the only op-contract change, and it is additive (optional request flag + optional result field). It does not alter single-frame `render` or the existing `render_sequence` PNG behaviour.

### Phase 2 — Penetration metric: `vrm_diff_engine::penetration`

New module, sibling to `positions` and `temporal`.

- Input: per-frame `Vec<SpringPositions>` (Phase 1) + a `ColliderSpec` describing the world-fixed collider(s) the suite authored (shape + world placement + radius). Because the collider is `WorldCoordinates`, its world pose is constant across frames — signed distance is direct.
- Signed distance per shape: sphere `|p − c| − r`; capsule `segment_distance(p, a, b) − r`. (Plane/inside variants deferred — Phase 3 uses sphere + capsule.)
- Output `PenetrationReport`: `max_penetration_depth_m` (= `−min` signed distance over all joints × frames, clamped at 0), `worst_frame`, `worst_joint`, `worst_spring`, and `passed = (max_penetration_depth_m ≤ ε)`.
- Tolerance `ε`: a small fixed margin (e.g. 2 mm) absorbing solver rest-penetration / numerical slop, documented in the methodology pin; the sweep is calibrated so a real tunnel is ≫ ε.
- Exposed via a runner subcommand `penetration-diff --positions <json> --collider <spec-from-plan> [--epsilon] --json`, exiting non-zero on failure (mirrors the standalone `diff` subcommand's exit-gating). The `ColliderSpec` is derived from the test plan / asset meta the suite emitted, so the metric never trusts the renderer for collider geometry.

### Phase 3 — Parametric CCD asset sweep

`spring_bone_ccd_sweep()` (in `sweep.rs`, mirroring the existing collider/multichain sweep style) + an `emit-springbone-ccd-sweep` CLI subcommand + `build_spring_bone_ccd_test_plan` sidecar.

- Geometry: a chain (reuse the existing chain primitive) + one `WorldCoordinates` collider positioned in the chain's swept column so the fast root translation drags the chain through it.
- Sidecar: a `render_sequence` block with `capture_positions: true`, a **fast** root animation (default ≈ 1.0 m over ≈ 0.1 s → ≈ 16 cm per 60 Hz substep), `tone_mapping: none`, settle from rest first. PNG capture may be disabled or kept minimal — the signal is positions, not pixels.
- Sweep axes that **straddle the tunnelling threshold** (per-substep displacement vs collider thickness):
  - collider radius: thin → thick (e.g. `{0.005, 0.02, 0.05}` m),
  - sweep speed: a few displacement/duration pairs spanning per-substep displacement below and above the radii,
  - collider shape: sphere, capsule,
  - (optionally) chain stiffness, since a stiffer chain resists penetration.
- Naming: `ccd_*` (e.g. `ccd_sphere_r0p02_v_fast`). Bounded to a small per-PR-diffable count, like the other sweeps.
- The design intent, asserted by the metric: above threshold a non-CCD solver tunnels (`max_penetration_depth ≫ ε`), a CCD solver does not. The sweep therefore **maps each renderer's tunnelling onset**.

### Phase 4 — Cross-renderer run + findings

Run the sweep through the adapters (per-op adapters certainly; UniVRM if Phase 1 batch capture lands), apply `penetration-diff` per cell, and write a `docs/findings.md` entry tabulating each renderer's `max_penetration_depth` vs collider-radius × speed — i.e. where each solver's tunnelling begins. **There is no golden here** — with an absolute metric every renderer is a subject; UniVRM is a peer, not the reference. The deliverable is a per-renderer tunnelling-onset table and a pass/fail at each cell.

### Methodology pin (`docs/methodology.md`)

Record a deliberate addition: (a) a **fast-motion regime** distinct from the swing sweep's drag/inertia regime, with the per-substep-displacement-vs-collider-thickness rationale; (b) a new **geometric non-penetration metric class** (absolute, oracle-free), distinct from SSIM/consensus and from `diff_positions`' drift-vs-reference; (c) the `ε` tolerance and its justification; (d) determinism via the existing 60 Hz fixed-step / settle-from-rest convention.

## Components & boundaries

- `crates/vrm-ops` — `render_sequence` params gain `capture_positions: bool`; `RenderSequenceResult.frames[]` gain optional `spring_positions`. (Op-contract source of truth.)
- adapters ×4 — populate per-frame `spring_positions` in their existing `render_sequence` loop when requested (UniVRM best-effort).
- `crates/vrm-runner` — persist per-frame positions to `<id>_<renderer>_positions.json`; new `penetration-diff` subcommand; thread `capture_positions` through the sequence dispatch.
- `crates/vrm-diff-engine` — new `penetration` module (`ColliderSpec`, signed-distance per shape, `PenetrationReport`).
- `crates/vrm-asset-generator` — `spring_bone_ccd_sweep`, `emit-springbone-ccd-sweep`, `build_spring_bone_ccd_test_plan`.
- `docs/methodology.md`, `docs/findings.md` — pin + results.

Each unit is independently testable: signed-distance math (pure, table-driven unit tests with hand-computed expectations); the sweep registry (count/axes/threshold-straddling); the sidecar pins (fast regime + capture flag); per-adapter per-frame capture (a known sweep → non-empty per-frame positions); the cross-renderer run is the manual deliverable.

## Risks / honesty

- **The render_sequence-result extension is adapter work ×4** — the bulk of the lift, and exactly the "large subsystem" the winding-down stance was wary of. It is additive and rides the existing frame loop, but every adapter is touched and re-validated.
- **UniVRM per-frame positions from the batch path** may not be cleanly feasible → best-effort; the absolute metric does not require it.
- **Determinism** of the fast regime must hold under the fixed-step convention; if an adapter's sequence stepping is not the methodology's 60 Hz fixed step, penetration depth could vary run-to-run — to verify per adapter.
- **Tolerance calibration:** `ε` must be above legitimate rest-penetration but well below a real tunnel; the radius/speed sweep is designed to leave a wide margin, but the first run should confirm the gap empirically before the threshold is trusted.

## Explicitly out of scope

- Animating the collider/limb directly (a per-node animation op) — rejected in favour of root-animation + world-fixed collider to avoid a brand-new op on all adapters.
- Cross-renderer consensus / SSIM for CCD — the metric is absolute; consensus is not used here.
- Plane / inside-sphere / inside-capsule colliders in the CCD metric — Phase 2 covers sphere + capsule; others deferred.
- Self-collision (chain-vs-chain) tunnelling — only chain-vs-collider is in scope.

## Rollout order

1. Phase 1 (capture extension) — ops + runner + adapters; unblocks everything.
2. Phase 2 (metric) — pure-Rust engine + runner subcommand; CI-gated, no renderer needed.
3. Phase 3 (sweep + sidecar) — pure-Rust; CI-gated.
4. Phase 4 (cross-renderer run + findings + methodology pin) — local, real adapters.

Phases 2–3 are pure-Rust and independently verifiable before any adapter renders; Phase 1 is the integration-heavy gate; Phase 4 is the VMK-facing deliverable.
